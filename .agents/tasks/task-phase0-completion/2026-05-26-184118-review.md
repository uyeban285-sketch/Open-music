# NestJS auth module with NextAuth frontend integration (v2)

All seven issues from the v1 review have been addressed: RLS middleware now uses `Prisma.sql` tagged template, the frontend type declarations align with the Prisma `UserRole` enum (`listener`/`enthusiast`/`power_user`/`admin`), refresh failure sets a `RefreshAccessTokenError` sentinel surfaced to the session, rate limiting uses INCR-first with TTL on first increment, `NEXTAUTH_SECRET` appears in `.env.example`, register catches `P2002` for a clean 409, and logout is guarded by `JwtAuthGuard` with ownership verification via `req.user.userId`.

**Watch for:** The frontend `authApi.logout()` doesn't send an `accessToken`, so the newly-added `JwtAuthGuard` on the logout endpoint will reject all client-side logout calls with 401 (confirmed). Rate limiter keys include unsanitized user-supplied email, enabling key-space pollution and per-victim lockout by an attacker who varies the email field (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The logout ownership fix introduced a coordination gap: the backend now requires a Bearer token on `POST /auth/logout`, but the only client (`authApi.logout`) doesn't accept or pass an `accessToken` parameter. Any frontend logout flow that uses this client will receive a 401 before the refresh token is ever checked.

The INCR-first rate limiter fixes the TOCTOU gap but inherits a new vector from including the raw `req.body.email` in the Redis key. An attacker can target a victim by sending login attempts with the victim's email from their own IP, exhausting the `{attackerIP}:{victimEmail}` bucket harmlessly, but more importantly an attacker can flood Redis with unique keys by varying the email, since no length/format gate exists before the INCR call.

1. **Logout client missing accessToken** — `authApi.logout()` doesn't pass an `accessToken`, so the `JwtAuthGuard` on the controller's `@Post('logout')` rejects all calls. Add an `accessToken` parameter to the client method and pass it as the Bearer header.

Truncate or hash the email component of the key, or validate email format before reaching the middleware.

## Logout endpoint unreachable from frontend client

The controller applies `@UseGuards(JwtAuthGuard)` to `POST /auth/logout` and extracts `req.user.userId` for ownership verification — correctly fixing the v1 issue. However, the corresponding frontend client:

```typescript
logout(refreshToken: string) {
  return apiFetch<void>('/api/auth/logout', {
    method: 'POST',
    body: { refreshToken },
  });
}
```

never sets `accessToken` in the options, so `apiFetch` never attaches an `Authorization` header. The guard rejects the request before the body is even parsed. The `me()` method demonstrates the correct pattern — it accepts and passes `accessToken`. The `logout` method needs the same treatment.

## Rate limiter key includes raw user input

The key construction `rate_limit:login:${ip}:${email}` uses the email value from the request body without any validation gate. The Zod pipe on the login route validates _after_ the middleware runs (middleware fires first in NestJS lifecycle). This means:

- An attacker can submit arbitrarily long strings as `email`, creating large Redis keys and memory pressure.
- Different emails create distinct counters, so the rate limit offers no protection against credential-stuffing attacks that rotate the target email.

The second point is partly by design (limiting per-account brute force), but the absence of any key-length bound or format check before Redis sees the value is the actionable concern. Hashing the email (e.g., SHA-256 truncated to 16 bytes) would bound key size without changing the semantics.
