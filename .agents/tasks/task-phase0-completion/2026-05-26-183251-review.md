# NestJS auth module with NextAuth frontend integration

This change stands up a complete authentication stack: a NestJS backend module providing register/login/refresh/logout/me endpoints with argon2id hashing, JWT access tokens (15 min), opaque refresh tokens stored in Redis (30 days, rotated on use), and IP+email rate limiting on login. The frontend integrates via NextAuth's CredentialsProvider with silent token refresh, Zod-validated login/register pages, and Next.js middleware for route protection. Infrastructure additions include Prisma schema, Redis service, KMS stub, health checks, and a global ProblemDetails exception filter.

**Watch for:** SQL injection in the RLS middleware via `$executeRawUnsafe` with string interpolation (confirmed). Role enum mismatch between Prisma schema (`listener`/`enthusiast`/`power_user`/`admin`) and frontend type declarations (`user`/`admin`) will cause runtime type confusion (confirmed). Silent failure on token refresh leaves stale credentials in the session with no signal to the user (confirmed).

## High-level view

The backend auth service uses argon2id for hashing, UUID v4 for refresh tokens stored in Redis with a 30-day TTL, and JWT signed with a static secret for access tokens. The rate-limit middleware gates login attempts per IP+email combo using Redis GET+INCR, but the check and increment are not atomic, allowing burst bypass under concurrency.

The frontend wraps the backend's token pair inside NextAuth's JWT session with a 14-minute internal expiry timer and proactive refresh via the JWT callback. When refresh fails, the callback silently returns the stale token — the session appears valid to the user even though the access token is expired and useless.

The Prisma schema defines four user roles (`listener`, `enthusiast`, `power_user`, `admin`) but the frontend TypeScript declarations and the shared package both narrow the role type to `'user' | 'admin'`. The backend's `getMe` endpoint returns `user.role` directly from Prisma, so the frontend will receive values that don't match its own type definitions.

The RLS middleware uses `$executeRawUnsafe` with string interpolation of `userId`. Although not wired to routes yet, it's a SQL injection vector waiting to be activated if the JWT secret is compromised or the middleware is applied to other user-id sources.

<details>
<summary>Issues (7)</summary>

1. **SQL injection in RLS middleware** — `$executeRawUnsafe` interpolates `userId` without parameterization. Use `$executeRaw` with Prisma's tagged template or validate UUID format before interpolation.
2. **Role enum mismatch** — Prisma defines `listener`/`enthusiast`/`power_user`/`admin`; frontend types expect `user`/`admin`. The `getMe` endpoint will return values the frontend can't handle correctly. Align the type definitions or add a mapping layer.
3. **Silent refresh failure** — When `authApi.refresh()` throws in the NextAuth JWT callback, the catch block returns the stale token. The session appears valid but the access token is expired. Surface the failure so downstream code can redirect to login.
4. **Rate limiter increments after check** — The counter is incremented after the check passes, not atomically with it. Under high concurrency, more than 5 requests can slip through before any sees a count of 5. Use a Lua script or `INCR`-first pattern to make check+increment atomic.
5. **No NEXTAUTH_SECRET in env schema** — The API's `env.schema.ts` validates `JWT_SECRET` but the web app has no equivalent validation for `NEXTAUTH_SECRET`. If it's missing, NextAuth falls back to insecure defaults in dev but fails silently in production.
6. **Register race condition** — `findUnique` then `create` is not atomic. Two concurrent registrations with the same email can both pass the check, and the second will throw an unhandled Prisma unique constraint error instead of a clean 409.
7. **Refresh token stored without user binding in logout** — The `logout` endpoint accepts any valid UUID and deletes the corresponding Redis key without verifying that the caller owns that token. An attacker with a leaked refresh token can invalidate another user's session.

## SQL injection in RLS middleware

The `RlsMiddleware` at `apps/api/src/common/middleware/rls.middleware.ts` line 19 executes:

```typescript
await this.prisma.$executeRawUnsafe(`SET LOCAL app.user_id = '${userId}'`);
```

The `userId` comes from `req.user?.id`, populated by the JWT strategy's `validate` returning `payload.sub`. A malformed or tampered JWT (weak/compromised secret) could inject arbitrary SQL into the SET LOCAL statement. Prisma's `$executeRaw` tagged template parameterizes values safely; switching to it eliminates this class of vulnerability.

## Role enum divergence between backend and frontend

The Prisma schema defines:

```
enum UserRole { listener, enthusiast, power_user, admin }
```

The frontend's `next-auth.d.ts` declares the role type as `'user' | 'admin'`. The shared package's `userSchema` uses `z.enum(['user', 'admin'])`. The backend's `getMe` endpoint returns `user.role` directly from Prisma, so actual API responses contain `"listener"`, `"enthusiast"`, etc.

This affects the JWT token too: `generateTokens` signs `{ sub: userId, role }` where `role` is the Prisma enum value. Frontend code expecting `'user' | 'admin'` will silently pass through `"listener"` since TypeScript types aren't enforced at runtime, but any conditional logic (`if (role === 'user')`) will never match for non-admin users.

## Silent refresh failure in NextAuth JWT callback

In `apps/web/src/lib/auth.ts`, the JWT callback's refresh path:

```typescript
try {
  const refreshed = await authApi.refresh(token.refreshToken);
  // ...
} catch {
  // Refresh failed - token will be stale, user will need to re-login
}
```

After this catch, the function returns the stale token with an expired `accessToken`. The NextAuth session still looks valid from the frontend's perspective, but downstream API calls will receive 401s. A common pattern is to set a sentinel (e.g., `token.error = 'RefreshAccessTokenError'`) and check it in the session callback so the UI can redirect to login.

## Rate limiter TOCTOU gap

The rate-limit middleware reads the current count with `GET`, compares it to the threshold, then increments with `INCR` in a separate `MULTI` block. Between the `GET` and the `INCR`, concurrent requests sharing the same key can all see a count below the limit and proceed. Under burst conditions (automated attacks), this allows significantly more than 5 attempts to succeed.

The fix is to `INCR` first and check the returned value: if it exceeds the limit, reject. If it's the first increment (value === 1), set the TTL.

## Register endpoint race condition

`auth.service.ts` performs `findUnique` + `create` as two separate queries. Under concurrent registration with the same email, both requests pass the check (both see `null`), then one `create` succeeds and the other throws a Prisma `P2002` unique constraint error. This propagates as an unhandled 500 instead of the intended 409 with ProblemDetails.

Wrapping the `create` in a try-catch for `P2002` (or using a transaction with serializable isolation) would produce the correct error response.

## Test coverage gaps

Not tested: the auth controller (HTTP-level integration), the ProblemDetails filter, the Zod validation pipe on malformed input, the NextAuth configuration and callbacks, the middleware route protection logic, the register race condition, and the rate-limiter concurrency gap.

## Unguarded logout endpoint

The `POST /auth/logout` endpoint has no `@UseGuards(JwtAuthGuard)` decorator. It accepts a `refreshToken` UUID in the body and deletes the corresponding Redis key without verifying caller ownership. If a refresh token is leaked (e.g., via XSS), anyone can invalidate another user's session without authenticating.
