# NestJS auth module with NextAuth frontend integration (v3)

This change delivers a full authentication stack: NestJS backend with argon2id hashing, JWT access tokens (15 min), Redis-backed opaque refresh tokens (30 days, rotated), IP+email rate limiting on login, and a NextAuth CredentialsProvider frontend with proactive token refresh. All nine issues from prior review passes have been addressed.

**Watch for:** No blocking concerns remain. The KMS service stores DEKs in an in-memory Map (ephemeral, non-persistent), which is explicitly documented as a dev stub and not wired to any auth flow. The `refresh` endpoint's GET-then-DELETE is not atomic, but the UUID4 token space makes collision/replay negligible in practice.

**Verdict**: APPROVED

## High-level view

The auth service catches Prisma P2002 for a clean 409 on duplicate registration and binds logout to the authenticated user via JwtAuthGuard plus Redis ownership verification. The refresh flow rotates tokens on every use (delete old, issue new).

The rate limiter applies INCR-first semantics with SHA-256 hashing (16 hex chars) of the email component and rejects emails over 254 characters before reaching Redis, bounding key size regardless of input.

The frontend's NextAuth JWT callback sets a `RefreshAccessTokenError` sentinel on refresh failure, surfaced to the session so downstream UI can redirect to login. The `authApi.logout()` client now accepts and passes `accessToken` for the Bearer header.

## Prior issue resolution

All v1 issues (SQL injection, role mismatch, silent refresh, TOCTOU rate limiter, missing NEXTAUTH_SECRET, register race condition, unguarded logout) were fixed in the first revision. Both v2 issues (logout client missing accessToken, rate limiter key-space pollution) were fixed in the second revision. Verified in current HEAD:

- `authApi.logout(refreshToken, accessToken)` passes both parameters, with `accessToken` attached as the Bearer header via `apiFetch`.
- `LoginRateLimitMiddleware` hashes email with `createHash('sha256').update(rawEmail).digest('hex').slice(0, 16)` and short-circuits to `'invalid'` for emails exceeding 254 characters.
- RLS middleware uses `Prisma.sql` tagged template for parameterized execution.

## Remaining design notes (non-blocking)

The KMS service uses an in-memory `Map<string, Buffer>` for DEK storage. Keys are lost on process restart, making any data encrypted with this service unrecoverable across deploys. This is documented as a dev-mode stub and the service is not consumed by the auth flow, so it presents no production risk at this stage.

The `refresh` endpoint performs `redis.get(key)` followed by `redis.del(key)` as separate commands rather than an atomic `GETDEL`. Under extreme concurrency with the same refresh token, two requests could both read the userId before either deletes, issuing two new token pairs. Given the token is UUID4 (2^122 bits of entropy) and only the legitimate client possesses it, this is not exploitable in practice.
